# ADR-0007 — The skill is the source of the method; its scripts are vendored here at a named commit

**Status:** Accepted · 2026.11.15
**Chosen by:** the custodian, 2026.11.15, who settled `PLAN.md` D2 as recommended by accepting this record. It is
needed from Phase 1a, because ADR-0015's results are made by the skill's generator.
**State:** Planned. The scripts are vendored in Phase 1a, and the server uses them from Phase 3.
**Depends on:** ADR-0001.
**Relates to:** ADR-0004 (the variables the scripts read), ADR-0006 (results files only through generators),
ADR-0008 (the server imports `tla_common.py`), ADR-0015 (its results are made by the skill's generator).
**Pending:** none.

---

## Context

The `writing-tla-specs-and-proofs` skill lives in TOPAK, under `skills/`. Its scripts are the method: how to run
a row, how to build a row list, how to make proof results, how to flip a hypothesis, how to sync proofs. They
need only the Python standard library, and they work without Docker. tla-kit needs them at a known version:
first for the generator that makes `spec/PinLifecycle.tla`'s results (ADR-0015), from Phase 1b, and then inside
the image for the MCP server.

## Decision

1. **The skill is the source of the method.** The server calls the skill's scripts, and imports `tla_common.py`
   for shared parsing. It does not reimplement them.
2. **The scripts are vendored into this repository at a named TOPAK commit.** The commit is recorded in a pin
   file beside them, with a sha256 of each file.
3. **CI checks the vendored files against the named commit by digest,** and fails when they differ. Moving the
   commit is a change with its own pull request.
4. **The skill stays usable without Docker.** Nothing in the skill depends on tla-kit, and a fix to a script is
   made in TOPAK first and then vendored.

## Consequences

- There are two copies of the method, and they can drift. Item 3 is the guard, and a drift is a failing check,
  not a silent difference.
- A fix to the skill reaches the server only when this repository moves its pin, and the image is then rebuilt.
- Fixes that the skill's scripts need for TOPAK are made in TOPAK. One is known: the scripts read
  `binary_sha256`, where TOPAK's `tools/TLAPS-PIN` has `binary_sha256_16` (F-9). It is planned for Phase 2.

## Alternatives not taken

- **Mount the skill at run time.** The server's behaviour would then depend on whatever checkout is mounted, and
  the image's digest would no longer describe it.
- **Fetch the scripts at build time from TOPAK at a commit.** This is close to item 2, but the build would depend
  on TOPAK being reachable, and a review here would not show what changed.
- **Package the skill's scripts as a Python package.** That adds a release process to the skill for one consumer.
- **Reimplement the method in the server.** That breaks rule 3, and makes two methods to keep in step, not two
  copies of one.
