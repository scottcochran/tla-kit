# ADR-0008 — The MCP server is Python over stdio, inside the image, confined to the mounted project

**Status:** Accepted · 2026.11.16
**Chosen by:** the assistant, but for item 1's standard library, which the custodian chose on 2026.11.16 over the
MCP SDK. Open to change.
**State:** Planned, Phases 3 and 5. No server exists.
**Depends on:** ADR-0001, ADR-0006, ADR-0007.
**Relates to:** ADR-0009 (the proof tools), ADR-0013 (pins: the server adds none), ADR-0014 (a server tool is a
MINOR release).

---

## Context

The server has to call the skill's scripts and import `tla_common.py` (ADR-0007). It has to run the same way in a
local agent session and in a GitHub Actions job. The Claude Code action takes MCP servers through `claude_args`,
as `--mcp-config`, with every tool named in `--allowedTools` (F-11). Its documents show `npx` and `uv` servers and
no `docker run` one. That rests on a fetch agent's report and was not tried.

## Decision

1. **The server is written in Python, with the standard library only,** as the skill's scripts are. It runs
   inside the image, started as `tla-kit mcp`. It speaks MCP's stdio transport itself: JSON-RPC 2.0, one message
   per line, with `initialize`, `tools/list`, `tools/call` and `ping`. It names the protocol version it speaks,
   and the client test checks it. Nothing is added to the image for it, so it adds no pin to `PINS.json`.
2. **The transport is stdio.** A client starts it as `docker run -i --rm --user "$(id -u):$(id -g)" -v
   <project>:/work <image@digest> tla-kit mcp`. The `--user` lets `tlc_rows` write its results file into a
   project owned by another uid, as on a GitHub runner (uid 1001); the image's `HOME` is world-writable.
3. **Every path a client sends is confined to the mounted project.** A path outside `/work`, after resolving
   links, is refused. The server itself reads the skill's scripts at `/opt/tla-kit/skill`.
   The server's own scratch and cache directories are outside the project (ADR-0006).
4. **The first tools are the model-checking tools of Phase 3:** `info`, `parse`, `symbols`, `evaluate`,
   `tlc_run`, `simulate`, `coverage`, `state_graph` and `tlc_rows`. The proof tools follow in Phase 4 (ADR-0009).
5. **Each tool returns what the command it stands for would conclude.** `tlc_run` and `tlc_rows` stand for the
   skill's scripts, and `tlc_rows` is compared by its results file, byte for byte (ADR-0006 item 1). `info` stands
   for `tla-kit-info --json`. The others stand for SANY or TLC run on the command line with the same options,
   and `simulate` with the same seed. Phase 3 is done when each returns the same verdict as its command on TOPAK's
   `Alone` and `Coupling`, and an MCP client test in CI drives every tool against the fixture.
6. **The skill's plugin declares the server by image digest** (Phase 5). The skill says which tool answers which
   step of its workflow, and what to do when Docker is absent. One configuration serves a local session and an
   Actions job.

## Consequences

- Python matches the skill. Nothing is translated, and the server's tests can reuse the skill's fixture.
- The standard library keeps the image's inputs as they are: no `pip`, no dependency tree to pin, and no
  bytecode written at build time to put the one-digest build at risk (ADR-0014 item 8). The cost is that the
  server follows MCP's specification itself. A new protocol version is a change to the server, and a MINOR
  release.
- Stdio needs no port and no network inside the container. A runner needs only Docker.
- Two things are recalled and not checked, and Phase 5 has to test them: that a Claude Code plugin can declare
  an MCP server, and that a `docker run` command works as an MCP server in the action.
- Start-up pays for a container per session. That has not been measured.

## Alternatives not taken

- **The MCP SDK, pinned by hash,** as first drafted. It brings about a dozen packages, compiled `pydantic-core`
  among them, each a pin under ADR-0013 item 7, and `pip` into the image.
- **Go or TypeScript,** as `marco6/tlapm-mcp` and `richashworth/tlaplus-mcp` use. Either would mean
  reimplementing the skill's scripts or calling them across a process boundary for every operation.
- **HTTP transport, as a long-running service.** It suits a shared server. It adds a port, a lifecycle and
  authentication, for a server that serves one project at a time.
- **The server outside the image, calling `docker run` for each tool.** That makes one container per call, and
  splits the server's version from the tools' digest.
