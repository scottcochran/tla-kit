# ADR-0013 — Every pin moves by one rule: one pull request, evidence that fits what the pin can change

**Status:** Proposed · 2026.11.15
**Chosen by:** the assistant. `PLAN.md` lists it among the records to accept before Phase 1c. The schedule, the
scanner and the refresh interval are proposals and open to change.
**State:** Planned, Phase 1c. Since Phase 1a the `Dockerfile` pins the base by digest, the `apt` snapshot by date,
both downloads and the `tlapm` binary by sha256. The skill's scripts are vendored at a named commit. Only the
prover has a rule for moving. No inventory file exists: `/opt/tla-kit/build-args` in the image stands in for it,
and the README's table of tools is written by hand.
**Depends on:** ADR-0002 (every tool held to a digest), ADR-0005 (the prover's two runs).
**Relates to:** ADR-0003 (the base), ADR-0007 (the vendored scripts), ADR-0008 (the MCP SDK), ADR-0012
(variants), ADR-0014 (what a release records, and the list of projects served).
**Pending:** the custodian's acceptance, which waits on ADR-0015's rows (its item 7).

---

## Context

ADR-0002 makes every download a pin and every pin move a change of image digest. Only ADR-0005 says what has to
be shown before a pin moves, and only for the prover. Phase 1 adds pins that no record says how to move: the
base image digest and the `apt` snapshot date. ADR-0007 and ADR-0008 add two more: the vendored scripts' commit
and the MCP SDK's hash.

Pins differ in what a move can change. A new `tla2tools.jar` can change what TLC finds, just as a new `tlapm`
can change what proves. A new base layer or `apt` snapshot changes the runtime, and should change no verdict.
The evidence a move needs follows from that. At the spike, TOPAK's `pr` TLC tier took 3,390 s run one module
after another. Its full proof run took 539 s.

Four places hold some of what is pinned, but none holds all of it, and nothing checks that they agree:
- **The `Dockerfile`'s build arguments:** a version, a sha256 and a URL, for the two downloads only.
- **The README's table:** written by hand, with shortened digests and no sources.
- **`tla-kit-info`:** the digests it measures for the jar and the `tlapm` binary, and the backends by version only.
- **Item 1 of this record:** the pins' names, with no values.

Nowhere records whether upstream still serves a build. That gov-tla's c8ddc44 tarball can no longer be
downloaded is known only from the session record (F-5). Nowhere records when a pin was taken, either. For a
rolling tag the date is part of what the pin means: "ff40755, as served on 2026.11.15" is in the README's
prose and nowhere else.

Pinning the base by digest and `apt` by date makes the image reproducible. It also freezes the image's security
fixes at the day of the pin. No record says when they are refreshed. The image runs offline tools over a mounted
project, and its server speaks over stdio with no port (ADR-0008), so its exposure is small. Small is not
nothing, and tla-kit publishes the image for others to run (ADR-0010).

## Decision

1. **The image's pins are these.** No other input to the build is left free.

   | Pin | Where it is set | Kind |
   |---|---|---|
   | `tla2tools.jar` | `TLA2TOOLS_VERSION`, `TLA2TOOLS_SHA256` | Checker |
   | `tlapm` and its bundled backends | `TLAPM_TAG`, `TLAPM_SHA256`, the kept tarball (ADR-0005) | Checker |
   | JRE major version | the base image's tag | Checker |
   | Base image | `BASE_IMAGE`, by digest (Phase 1) | Runtime |
   | `apt` packages | the snapshot date (Phase 1) | Runtime |
   | MCP SDK and any other Python package | hashes (ADR-0008) | Runtime |
   | The skill's scripts | the vendored commit (ADR-0007) | Method |
   | A variant's tool | its own digest (ADR-0012) | Checker, for that variant |

   The JRE is counted as a checker because TLC runs on it. A JRE major move is a checker move. A patch release of
   the same major, arriving with a base refresh, is a runtime move. The table is kept, with its values, as the
   inventory of item 7.

2. **One pull request moves one pin.** The base digest and the `apt` snapshot date move together, as one runtime
   refresh. The pull request names the old value, the new value, why it moves, and the evidence in item 3.

3. **The evidence fits the kind of pin.** Each run is made in the candidate image, over every project the image
   serves (the list in ADR-0014), at a named commit of each project.
   - **Checker:** the projects' committed evidence is regenerated and compared. For the jar or the JRE, that is
     each project's TLC results (TOPAK's `tools/check-results.sh` on the `pr` tier). For the prover, it is
     ADR-0005 item 4. The result is either no differences, or every difference listed and explained.
   - **Runtime:** the self-test, and the spike's checks repeated (Phase 1's "Done when"): the skill's setup
     check, TOPAK's pin check, and the full proof run. Every count has to equal the last release's.
   - **Method:** ADR-0007's digest check, and the MCP server's tests once the server exists.

   The evidence goes into the pull request, and from there into the release notes (ADR-0014).

4. **Upstream changes are found by a scheduled check, which reports and moves nothing.** A weekly workflow
   reports:
   - a new `tla2tools.jar` release;
   - a change to what the `tlapm` tag serves (ADR-0005 item 3);
   - a new digest behind the base image's tag;
   - the vulnerability scan in item 5.

   It reports by opening or updating one issue in this repository. A move starts from the issue, as a pull
   request under item 2. No bot merges a pin move.

5. **The current release is scanned for known vulnerabilities.** The scan runs weekly and in the release
   workflow (ADR-0014), with a scanner pinned like any other tool (Trivy is the proposal). The scan triggers a
   runtime refresh in two cases:
   - **On a schedule:** at least every 90 days, if the base or the snapshot has moved.
   - **Promptly:** when the scan finds a critical vulnerability with a fix available, in a package the image
     uses.

   A finding in the prover's bundled backends (Isabelle, Poly/ML, Z3, Zenon, LS4) is reported. It is not
   patched here. Those backends move only with the prover, under ADR-0005.

6. **A move here moves no project.** ADR-0005 item 5 applies to every pin. Each release says what kind of move it
   was, so a project knows what it would have to regenerate if it moved its own pin to that release.

7. **Every pin is listed, with its values, in one committed inventory: `PINS.json`.** It is the single source
   for what the image is meant to hold. For each pin it gives:
   - the tool, its version, and its kind (item 1);
   - the build arguments that set it;
   - where it is served from: the upstream URL, and the URL of the kept copy where there is one (ADR-0005);
   - the sha256 of what is downloaded;
   - the sha256 of each installed file a results file can cite. For the prover's tarball that is the `tlapm`
     binary, each bundled backend, and the second TLA+ tools jar `tlapm` uses (`backends/bin/tla2tools.jar`, a
     build apart from the checker), which the tarball's own digest does not name;
   - when the value was pinned, and by which pull request, or by which commit where there was no pull request;
   - a dated log of whether upstream serves it. Each entry says from what date a state held.

   For a runtime refresh, the entry gives the base image's digest, the tag it was resolved from and the date it
   was resolved. A tag such as `eclipse-temurin:25-jre-noble` points at a different digest every few weeks, so
   the digest alone does not say which tag it came from, or on what day. The entry also gives the snapshot
   date and the resolved versions of the packages the `Dockerfile` installs by name (`python3`, `perl`, `git`).
   The full package list is in the release's SBOM (ADR-0014).

   Entries look like this. The base's values are fixed in Phase 1.

   ```json
   {
     "tool": "tlapm", "kind": "checker", "version": "1.6.0-pre at ff40755",
     "set_by": ["TLAPM_TAG", "TLAPM_SHA256"],
     "upstream": "https://github.com/tlaplus/tlapm/releases/download/1.6.0-pre/tlapm-1.6.0-pre-x86_64-linux-gnu.tar.gz",
     "kept_copy": null,
     "download_sha256": "99db29f1…6bcc",
     "installed": {"/opt/tlaps/bin/tlapm": "6182df63…5bb2", "…": "…"},
     "pinned": {"date": "2026.11.15", "by": "commit 770daf2"},
     "served": [{"from": "2026.11.15", "upstream": true}]
   }
   {
     "tool": "base", "kind": "runtime",
     "set_by": ["BASE_IMAGE"],
     "resolved": {"tag": "eclipse-temurin:25-jre-noble", "digest": "sha256:…", "date": "…"},
     "apt_snapshot": "…",
     "packages": {"python3": "…", "perl": "…", "git": "…"},
     "pinned": {"date": "…", "by": "…"}
   }
   ```

   **The lineage is the inventory's history.** A pin's earlier values are `PINS.json` as committed at each
   earlier release tag, and in `main`'s history between those tags. That history is never rewritten
   (ADR-0014 item 1). The file holds current values with their dates. It is not a second copy of its own
   history. The served log belongs to the current value: when a pin moves, its new value starts a new log.

   Four checks keep it true:
   - **The `Dockerfile` and the inventory agree.** A CI check compares the build arguments' defaults with the
     inventory, and fails when they differ. A pin move changes both in the same pull request (item 2).
   - **The image carries its inventory.** It is copied to `/opt/tla-kit/PINS.json`. The self-test fails if
     any installed file's digest differs from it. `tla-kit-info` reports from it, so the image alone says what
     it holds and where each part came from, even to someone who has not seen this repository.
   - **The README's table is generated from the inventory,** and CI fails if the two differ.
   - **The release copies the inventory** as the pin table ADR-0014 item 3 records.

   **A change in the served state is added to the log by pull request.** Each week the check (item 4) confirms
   in its issue that nothing has changed, or reports a change: upstream has stopped serving a build, or now
   serves something different under the same name. Each weekly run is dated in the issue. A change is
   recorded by adding one dated entry to the log, which is never edited. That pull request moves no pin, and
   needs no evidence beyond the check's output.

## Consequences

- Every pin has one route and one standard of evidence. ADR-0005's runs become one case of a general rule.
- Checker moves are costly. A jar move costs about an hour of TLC per project, run one module after another, or
  less as a matrix. That cost is meant to make checker moves rare and deliberate.
- A runtime refresh changes the image digest without changing any tool. Results files name the image's digest
  (ADR-0002), so a project that moves to the new digest changes that line in each of its results files, though
  no verdict changes. A project may instead stay on its old digest. ADR-0014 keeps that digest available, but
  no security fixes are made to it.
- The weekly check needs the list of projects served and a scanner, and both are new things to keep. The issue
  it opens will sometimes report a move nobody takes. That is intended: the report shows the move is possible,
  and taking it is still a decision.
- Running the evidence over every project is fine at two projects. A third or fourth project would make it
  slow, and the rule may have to name a sample instead.
- A pin is written in two places, the `Dockerfile` and the inventory. The `Dockerfile` cannot read a JSON file
  for its defaults, so the second copy can't be avoided. Item 7's check turns a drift between them into a
  failing pull request.
- Whether a build can still be fetched becomes a fact in the repository, with the date it last changed. It is
  no longer something remembered from a session. A rebuild that would fail because upstream has moved can be
  seen ahead of time.
- For any date, the pins in force, when each was taken, and what upstream served then can all be read from
  the repository. The weekly confirmations stay in the issue, not in the file. The file records each change
  to the served state, not each week the state held.

## Alternatives not taken

- **A separate rule for each pin, as the records have now.** That is how the jar, the base and the snapshot
  were left without one.
- **Renovate or Dependabot opening and merging pin moves.** Neither can run the evidence in item 3. Merging
  automatically makes a move routine, when ADR-0002 makes it a decision. Dependabot is used for the workflows'
  Actions (ADR-0014). It is not used for the image's pins.
- **No schedule, moving only when something breaks.** Security fixes would then wait on an unrelated change.
  The drift from upstream would also be found during a rebuild, at the worst time.
- **Leave `apt` unpinned, to get fixes on every build.** That gives up reproducibility (ADR-0002 item 4) to get
  fixes no one has reviewed.
- **Generate the `Dockerfile` from the inventory.** That leaves one copy, but a generation step has to run
  before `docker build`. ADR-0003 item 3 requires plain `docker build .` to work.
- **Use the SBOM as the inventory.** An SBOM is made from the built image. It records what is in the image, not
  what was meant to be, and it holds no sources, kept copies or served state. It complements the inventory
  (ADR-0014 item 3) and does not replace it.
- **One pin file per tool, after TOPAK's `tools/TLA-PIN`.** That format suits a project pinning one or two
  tools. One file is easier to check, copy into the image and attach to a release. The projects keep their own
  pin files, which the inventory does not replace (ADR-0005 item 5).
