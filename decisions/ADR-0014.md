# ADR-0014 — Every pull request is built and tested; a release is an immutable tag, attested, and never deleted

**Status:** Proposed · 2026.11.15
**Chosen by:** the assistant. Not listed in `PLAN.md`'s decisions owed. The version scheme and the attestation
mechanism are proposals and open to change.
**State:** Planned, Phase 1 (CI, releases, attestation, the list of projects served) and Phase 2 (the projects'
own pins on the list). No workflow exists, and no GitHub Actions run has been tried.
**Depends on:** ADR-0010 (where and when the image is published), ADR-0013 (the kinds of move).
**Relates to:** ADR-0002 (the digest a project cites), ADR-0005 (the kept tarball), ADR-0007 (the vendored
scripts' check), ADR-0008 (the server's tests), ADR-0012 (variants). Item 5 sharpens ADR-0010 item 5.
**Pending:** the custodian's acceptance, and the licence check of ADR-0005, which an SBOM and a public image both
wait on.

---

## Context

ADR-0010 publishes from a tag, and records the digest in the release. It does not say what runs before a
release, what a tag's name means, or how a reader can tell that a digest was built from this repository. Its
item 5 keeps an image "while any project's pin names them", but nothing here knows which pins exist.

A digest is cited by a project's CI, by a reviewer, and by a reader of a results file years later (ADR-0010).
That reader is checking a results file in a project's history, so the citation must still resolve long after
the project has moved to a newer digest.

tla-kit has one custodian. Any promise of support has to be one person can keep.

## Decision

1. **Every pull request runs CI, and `main` merges only on a pass.** CI does these things, and pushes nothing:
   - builds the image with plain `docker build .` (ADR-0003 item 3), and every variant (ADR-0012);
   - runs the self-test;
   - runs the vendored scripts' check (ADR-0007), and the MCP server's tests once the server exists (ADR-0008);
   - for a pull request that moves a pin, carries the evidence ADR-0013 asks for.

   `main` is protected, and its history is not rewritten.

2. **A release is a version tag, and the tag is never moved or reused.**
   - **Who:** only the custodian pushes release tags. Tags matching `v*` are protected.
   - **Scheme:** `vMAJOR.MINOR.PATCH`, and the number says which kind of move the release holds (ADR-0013).

     | Part | When it changes | What a project that adopts the release has to do |
     |---|---|---|
     | MAJOR | A checker pin moved | Regenerate its evidence |
     | MINOR | A runtime refresh, or a new tool, variant or server tool | Change the digest its results files name; no verdict changes |
     | PATCH | Only the wrappers, `tla-kit-info` or the server changed; no pin moved | The same as MINOR |

   - **Before 1.0:** releases stay at `0.x` until Phase 2 is done, and while they do, a checker move may take
     a MINOR.
   - **Variants:** a variant is tagged `<version>-<variant>`, for example `v1.2.0-apalache`, and is built in the
     same workflow from the same tag.

3. **A release records what a reader needs to check a citation.** The GitHub release for the tag holds:
   - the digest of the base and of every variant;
   - the JSON output of `tla-kit-info`;
   - the full pin table (ADR-0013 item 1);
   - the kind of move, and its evidence;
   - the kept prover tarball (ADR-0005);
   - the vulnerability scan (ADR-0013 item 5);
   - an SBOM;
   - one line saying what a project must regenerate if it adopts the release.

4. **Every published digest is attested.** The release workflow makes these, through GitHub's artifact
   attestations:
   - a build-provenance attestation, tying the digest to this repository, the tag and the workflow run;
   - an SBOM attestation.

   Anyone can check a digest with `gh attestation verify`, without a key held here. Workflow permissions are
   least privilege. Only the release workflow can write packages, request an OIDC token, or write attestations.
   Every Action the workflows use is pinned by commit sha. Dependabot proposes moves of those Actions, and a
   person merges them.

5. **A released digest is never deleted.** This sharpens ADR-0010 item 5, from "while any project's pin names
   it" to "always". A citation in a project's history has to resolve whatever that project names today.
   - **A known problem:** when a release has one (an unsound prover case, a missed fix, a broken wrapper), its
     release notes say so, and it stays available.
   - **Withdrawal:** an image is withdrawn only for a legal reason, such as a licence problem. A withdrawal is
     recorded in the release and in a new record.
   - **Cleanup:** pull requests push no images, so nothing untagged builds up to clean.

6. **The projects served are listed here.** `CONSUMERS.md` names each project, and the file in it that holds its
   tla-kit pin. Today that is TOPAK and gov-tla. The list has two uses:
   - ADR-0013's evidence runs over the projects it names;
   - the weekly check (ADR-0013 item 4) reads each pin and reports which releases are in use.

   A project joins the list by a pull request here. Nothing is sent to the projects. A project learns of a
   release by watching this repository's releases.

7. **Only the latest release is supported.** A fix goes into a new release. An older release stays available
   under item 5, but no fixes are made to it.

## Consequences

- A broken default build or self-test stops a pull request, not a release. Phase 1's first check (ADR-0003
  item 3) becomes a check that runs on every pull request.
- The version number tells a project the cost of adopting a release before it reads the notes. That holds only
  if the custodian applies ADR-0013's kinds strictly.
- A reader can check, with no help from tla-kit, that a digest was built here, from which tag, and what is
  inside it.
- The registry only grows. At 806 MB a release (ADR-0001), with variants larger, storage depends on public
  images on GHCR staying free. If that changes, item 5 has to be revisited by a new record.
- `CONSUMERS.md` is one more file to keep current. A project that pins tla-kit without joining the list gets
  no evidence run before a move. Its pinned release is still kept, under item 5.
- One supported release suits one custodian. A project that stays on an old release does not get its security
  fixes (ADR-0013).

## Alternatives not taken

- **Date tags (`2026.11.15`).** They match the project's date style, but say nothing about what a project has to
  regenerate. The release notes would then be the only way to find out.
- **Signing with cosign and a key held here.** That means a key to keep, rotate and lose. GitHub's attestations
  are signed through Sigstore without one, and are checked with a tool the projects already use.
- **Delete images no project names any more.** A results file in a project's history would then cite a digest
  that does not resolve. That is the failure ADR-0010 exists to prevent.
- **Open a pull request in each project on every release.** That pushes moves the projects decide themselves
  (ADR-0005 item 5), and needs write access to repositories tla-kit does not own.
- **Publish a release candidate from every merge to `main`.** ADR-0010 already declined to publish from `main`.
  A candidate digest would only be one more thing that cannot be cited.
