# ADR-0015 — The pin and release process is specified in TLA+, and checked by TLC before the records it covers are accepted

**Status:** Accepted · 2026.11.15
**Chosen by:** the custodian (that the module is written); the assistant (what it models, its properties, its
rows, and the gate in item 7). Open to change.
**State:** Planned, Phase 1b, before Phase 1c's workflows. No module exists, and there is no `spec/` directory yet.
**Depends on:** ADR-0005, ADR-0013 and ADR-0014 (what is modelled).
**Relates to:** ADR-0002 (digests), ADR-0007 (the skill's method, by which the module is checked), ADR-0010 (the
registry), ADR-0016 (the other module).
**Pending:** none.

---

## Context

ADR-0005, ADR-0013 and ADR-0014 each describe part of one process. Several parties act in it, each at its own
time and without waiting for the others:

- **upstream,** which rebuilds a tag under the same name, or stops serving a build;
- **the weekly check,** which reports what upstream does, and files changes to the served state by pull request;
- **the custodian,** who opens and merges pull requests and pushes release tags;
- **CI,** which builds and tests each pull request;
- **the release workflow,** which builds from a tag, then publishes, attests and records;
- **the projects,** which pin a release when they choose, and keep that pin in their history.

Each record reads correctly on its own. What can go wrong lies in the order the parties act. A reading of the
three records with that in mind found four gaps:

1. **The evidence can be for an image that is never released.** ADR-0013 item 3 runs the evidence "in the
   candidate image". ADR-0014 item 1 merges on a pass. It does not say that a pull request is tested against the
   `main` it merges into. Two pull requests, one moving the jar and one refreshing the base, can each pass against
   the same `main`, and both can merge. The image `main` then builds holds both moves, and no evidence was run on
   it.
2. **A pull request that moves the prover has no kept copy to build from.** ADR-0005 item 2 keeps the tarball as
   a release asset and builds from it. ADR-0014 item 3 attaches the tarball to the release, which exists only
   after the tag. CI runs on the pull request before any release holds the new tarball.
3. **Rebuilding depends on sources that no record keeps.** ADR-0014 says that a rebuild years later gives the
   same image. Only the prover's tarball has a kept copy. The base image by digest, the `apt` snapshot and
   `tla2tools.jar` stay with Docker Hub, Ubuntu and GitHub. No record says that it relies on them to keep serving.
4. **A served-log entry does not name the value it is about.** ADR-0013 item 7 starts a new log when a pin moves.
   A served-state pull request opened before a move and merged after it can file its entry under the new value.
   A merge conflict would probably catch this, but nothing requires one.

No model found these. A model would have to show each one as a behaviour, and would keep showing it while the
records change. The records are Proposed and still being edited: ADR-0013 and ADR-0014 each changed three times on
2026.11.15.

## Decision

1. **One module, `spec/PinLifecycle.tla`, specifies the process.** TLC checks it in the image. Its rows are in
   the skill's row-list form. Its results file is made only by the skill's generator (ADR-0007), and is compared in
   CI like any project's. It is tla-kit's first spec, and `spec/` follows TOPAK's layout.

   Until the first release, the image is one built from this repository at the commit under review. Its digest
   is not published, so the results are working output (ADR-0002 items 5 and 7). They are regenerated in the
   first published image, and are compared from then on as item 8 says.

2. **Each action comes from an item of a record, and names that item.**

   | Party | Actions | From |
   |---|---|---|
   | Upstream | serve a value; serve something different under the same name; stop serving | ADR-0005 Context; ADR-0013 item 4 |
   | Custodian | open a pull request that moves one pin, or the base and the snapshot together; merge it; push a tag | ADR-0013 item 2; ADR-0014 items 1 and 2 |
   | CI | build a pull request's candidate from the sources its pins name; run its evidence | ADR-0013 item 3; ADR-0014 item 1 |
   | Release workflow | build from the tag; publish the digest; attach the kept tarball, the inventory and the evidence | ADR-0005 item 2; ADR-0014 items 3 and 4 |
   | Weekly check | observe upstream; open a served-state pull request | ADR-0013 items 4 and 7 |
   | Registry | hold every published digest; withdraw one, with a record | ADR-0014 item 5 |
   | Project | pin a published digest; keep every pin it has had in its history | ADR-0014 items 5 and 6 |

   A change to a record that changes an action changes the module in the same pull request.

3. **Some things are abstracted away.**
   - **An image is the tuple of its pin values.** Two images are equal when their tuples are equal. Whether two
     builds of the same pins give the same bytes is ADR-0014 item 8's check, not the model's.
   - **Time is not modelled.** The weekly cadence and the 90-day refresh (ADR-0013 item 5) become fairness, not
     intervals.
   - **A version number is only as detailed as the scheme needs:** which part went up between two releases.
   - **The scan, the SBOM, the attestation, the licence notices and the copyleft parts' source (`PLAN.md` D7)
     are left out.** Each adds something to a release, and none changes the order of anything. The source
     archives travel with the kept tarball, so the kept-copy row covers when they are uploaded.

4. **The module states these properties.**

   Invariants:
   - **The evidence fits the release.** Every release's evidence was run on the image the release publishes.
   - **A build uses the source its record names.** A prover value is built only from its kept copy (ADR-0005
     item 2).
   - **Every release can be rebuilt.** Each of its pins is still served, or is kept here. A constant, `Durable`,
     names the upstreams that are taken to keep what they serve. What the records now leave unstated becomes a
     value each row states.
   - **Citations resolve.** Every digest a project has ever pinned is in the registry, or was withdrawn with a
     record.
   - **Tags do not move.** From its first publish on, a tag names one digest.
   - **The version fits the move.** From 1.0 on, a release whose checker pins differ from the previous release's
     has a higher MAJOR. One whose runtime pins differ has at least a higher MINOR.
   - **One move per pull request.** Every merged pull request moves one pin, or the base and the snapshot
     together.
   - **Each log entry is filed under the value it is about.** No entry changes once it is filed.

   Liveness, under weak fairness of the weekly check:
   - Every change upstream is eventually reported.

5. **There is a row for the records as written, and a row for each fix.**
   - **The records as they stand.** This row is expected to violate the properties behind gaps 1 to 4. Its
     expected outcome names those properties before the row is first run.
   - **One fix per gap,** each in its own row, and each expected to pass the property its gap violates. Examples:
     a pull request tested against the `main` it merges into; the kept copy uploaded before the pull request that
     names it; `Durable` naming Docker Hub, Ubuntu's snapshot archive and GitHub's releases; a log entry that names
     its value.
   - **Together, the two rows are a flip test.** The fix row passes and the as-written row fails, which shows that
     the property depends on the fix.
   - **The bounds are small, and each row states them:** three pins (the prover, the jar and the base, so that one
     checker pin has a kept copy and one does not), two values for each, two pull requests open at once, two
     releases, and one project.

6. **The module decides nothing in the records.** A fix is made in the record it belongs to, by a History row or
   a new record. The row that shows the fix then becomes an expected pass. The module is evidence for the records,
   and is regenerated when they change.

7. **ADR-0005, ADR-0013 and ADR-0014 are accepted only when every row has the outcome it expects.** A violation
   kept by choice is allowed only as a row whose expected outcome says so, with the reason given in the record it
   concerns. The rows that decide acceptance may be item 1's working output.

8. **CI regenerates the results on every pull request that changes `spec/` or `decisions/`, and compares them with
   the committed file.** This starts with Phase 1c's CI. Every checker move reruns the rows as part of its evidence
   (ADR-0013 item 3), because the image's own jar checks the module.

## Consequences

- Each of the four gaps becomes a behaviour that a reader can replay step by step, not an argument in prose.
- A change to a record that reopens a gap fails CI.
- The module is one more thing to keep in step with three records. Item 2's rule, that the two change together,
  is the guard. ADR-0014 item 1's list of what CI runs gains this check, by a History row there once this record
  is accepted.
- tla-kit becomes a user of its own image. The rows check that the image's TLC and the skill's generator work,
  beside the self-test.
- If the model passes, the process as modelled is right. That says nothing about whether GitHub, BuildKit or the
  registry behave as item 3 assumes. Branch protection, tag protection and BuildKit's timestamps are still checked
  by their own runs (ADR-0014).
- Acceptance of three records waits on a module that does not exist yet.
- Until the first release, that acceptance rests on results that cannot be cited (item 1). `PLAN.md` lists this
  as a risk.

## Alternatives not taken

- **Fix the four gaps in prose, without a model.** That would fix these four. The model earns its keep at the
  next edit: these records changed three times in one day, and a reading would have to be done again each time.
- **PlusCal.** The parties have no local control flow worth writing as a program. They are independent actions on
  shared state, which plain TLA+ states more directly.
- **Apalache.** It is not in the image (ADR-0012). At these bounds the state space should be small enough for TLC,
  though that has not been measured.
- **A TLAPS proof of the invariants.** The records are Proposed and still moving, and a proof would have to be
  redone after each move, for properties TLC checks at small bounds. If the records are accepted and stay stable,
  a proof would need a new record.
- **One module for this process and the `prove` tool (ADR-0016).** The two share nothing but the image, and they
  are written at different times.
- **Model GitHub's semantics in detail: merge refs, required checks, merge queues.** The gaps lie in the order of
  events, which the abstraction keeps. A fix that relies on a GitHub feature is checked by trying it in Phase 1.
