# ADR-0016 — The `prove` tool's requests, processes and cache are specified in TLA+ before the tool is built

**Status:** Accepted · 2026.11.16
**Chosen by:** the custodian (that the module is written, and in TLA+ without PlusCal); the assistant (what it
models, its properties, and when it is written). Open to change.
**State:** Planned, Phase 4. The server exists (Phase 3), but no `prove` tool and no module.
**Depends on:** ADR-0008 (the server), ADR-0009 (the design of `prove`, and item 5's choice of one `tlapm` per
request).
**Relates to:** ADR-0006 (no results file, and nothing written into the project), ADR-0015 (the other module, and
how modules are checked here).
**Pending:** none.

---

## Context

ADR-0009 item 3 asks for three things:
- a cache that the server owns;
- the whole process group killed on cancel or timeout;
- a success that needs exit 0, no error line and a non-zero obligation count.

Each of these is a rule about one request. But the server (ADR-0008) takes its requests over one stdio
connection. An MCP client can send several requests before the first is answered, and can cancel any of them.
In MCP a cancel is a notification, `notifications/cancelled`, naming the request. The specification of version
2025-06-18 says that it "may arrive after request processing has completed, and potentially after a response has
already been sent", that "both parties MUST handle these race conditions gracefully", and that a receiver SHOULD
"not send a response for the cancelled request". So the hard questions involve more than one request at a time:

- two `prove` calls on one module, or on two modules that extend a shared module, both using the server's cache;
- a cancel that arrives as `tlapm` exits, or after the response has been sent;
- a timeout while backends (Z3, Zenon, Isabelle) are still running under `tlapm`.

Getting these wrong gives answers that look right: a success for a run that was killed, backends still running
after the response, a cache written by two processes at once. None of these shows up in a test that sends one
request at a time. The runs are also long. `Mesh` took 152 s to prove at the spike, so requests will overlap in
ordinary use.

ADR-0009 item 5's comparison (`derived/tla-kit-prove-comparison-2026.11.16.md`) settled which processes exist.
The custodian chose `tlapm` per request on 2026.11.16: each `prove` call starts its own `tlapm --toolbox FROM TO`,
with `--cache-dir` set by the server, and reads the Toolbox protocol. There is no long-lived `tlapm_lsp`. The
comparison also found that `tlapm` exits 0 when an obligation fails: whether a run succeeded is read from its
output.

How `tlapm` behaves in these cases is still not known:
- whether two processes can share a cache directory;
- whether every backend stays in `tlapm`'s process group;
- what `tlapm` leaves in its cache when it is killed.

None of this has been checked.

## Decision

1. **One module, `spec/ProveRequests.tla`, specifies the tool's handling of requests.** It is checked as ADR-0015
   item 1 says: by TLC in the image, with rows in the skill's form, and with results made only by the generator. It
   is written in TLA+ directly, without PlusCal, at the custodian's choice: every action is written by hand, as in
   `spec/PinLifecycle.tla`.

2. **The module is written after ADR-0009 item 5's choice, and before the tool's code.** The choice is one
   `tlapm` per request, in a process group of its own, with a cache directory the server names. The module models
   that. A long-lived `tlapm_lsp` is not modelled.

3. **The module models these parts.**
   - **Requests:** received, waiting, running or answered. Each has a module and a scope: a step, a line range, a
     theorem, or the whole module.
   - **Processes:** `tlapm` and the backends it starts. Each is alive or not, and is in its process group or has
     left it.
   - **Cache directories,** and which live processes write to each one.
   - **Cancel and timeout,** each of which can arrive at any point, including after the response.
   - **How `tlapm` ends:** its exit code, whether it printed an error line, its obligation count, whether any
     obligation's status was `failed`, and whether its Toolbox output stopped part-way through a block. Exit 0
     with a failed obligation is a case, not an exception: the comparison saw it.
   - **The project,** as a set of files that the server may read and may not write.

4. **The module states these properties.**

   Invariants:
   - **At most one answer per request.** Each request gets at most one response, and nothing after it. A request
     the server cancelled gets none (MCP's cancellation, above). A cancel that arrives after the response changes
     nothing.
   - **Success only from a complete run.** A success response needs a run that ended by itself, with exit 0, no
     error line, no `failed` obligation, a non-zero obligation count, and no Toolbox block cut off part-way. A run
     that was killed is never a success.
   - **The answer's scope is the request's scope.** A step that was proved is not reported as a proved module
     (ADR-0006 item 2).
   - **No process outlives its request.** When a response is sent, no process that the request started is still
     alive.
   - **One writer per cache.** No two live processes write the same cache directory.
   - **Nothing is written into the project** (ADR-0006 item 3).

   Liveness, under weak fairness of the server's actions and of timeouts:
   - Every request is eventually answered or cancelled.
   - A request waiting for a cache eventually runs.

5. **There is a row for a naive design, and a row for the chosen one.**
   - **The naive design** is one shared cache with no lock, and the kill sent to `tlapm` alone. This row is
     expected to violate "One writer per cache" and "No process outlives its request".
   - **The chosen design** is expected to pass.
   - **A third row has a backend that leaves the process group.** What the server then does is a stated choice,
     not an accident.
   - **The bounds** are three requests and two modules. The cache is one directory in one row, and one directory
     per module in another.

6. **Each assumption about `tlapm` is tested in the image before the row that relies on it is fixed.** There are
   three: a cache shared by two processes, the process groups of the backends, and what a kill leaves in the cache.
   The row's comment names the test and gives its result. Where `tlapm` behaves differently from what a row
   assumes, the row and the design both change.

7. **The server's tests follow the properties.** For each invariant that a test can exercise, Phase 4's tests
   include one test that tries to break it. Examples: two concurrent `prove` calls on one module, a cancel during a
   run, a timeout while backends are running, and a cancel after the response. The module says which test goes
   with which property. The model does not replace the tests, and the tests do not replace the model.

## Consequences

- The tool's concurrency is designed before it is coded, while a change still costs one line of a module.
- Phase 4's "Done when" in `PLAN.md` includes the module's rows and item 7's tests. The plan puts this record's
  acceptance before the module and the tools, so they apply only once it is accepted.
- The module waited on ADR-0009 item 5, whose choice was made on 2026.11.16.
- A model that passes is only as good as item 6's tests of `tlapm`.
- The module has to be kept in step with ADR-0009 and with the server's code. A change to how the server handles
  requests changes the module in the same pull request.

## Alternatives not taken

- **Tests only, stress tests included.** A test finds a race only if that interleaving happens to run, and shows
  only the orders that did run. A model checks every order, at small bounds. The tests are kept as well (item 7).
- **Run every request one after another, one `tlapm` at a time.** That removes most of the questions, and it may
  turn out to be the design the module recommends. Here it is a row, not a rule decided in advance. Its cost is an
  agent waiting minutes behind an unrelated module.
- **Write the module after the code, from the code.** It would then check what was built rather than what was
  meant, and a fault in the design would cost a rewrite.
- **Add this to ADR-0015's module.** The two share nothing but the image, and they are written at different times.
