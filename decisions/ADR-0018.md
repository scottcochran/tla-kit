# ADR-0018 — tla-kit is the home of three independent skills, records, TLA+ and CI/CD, each enabled on its own and released with the image

**Status:** Proposed · 2026.11.20
**Chosen by:** the custodian: that the coupling lives here; ⟨Q7⟩ that the records, TLA+ and CI/CD skills are
separate skills, that their order is tla-kit's to decide, and that the owner of a decision is called the
custodian; ⟨Q12⟩ that each skill is enabled or disabled on its own, that tla-kit's design decides how a skill is
split, and that the CI/CD skill is decoupled from CI's gates (ADR-0020). The assistant chose the form below.
**State:** Planned. One of the three exists: the TLA+ skill, whose source is in TOPAK and whose scripts are vendored
here (`vendor/VENDOR-PIN`, TOPAK `6a26310`).
**Depends on:** ADR-0001.
**Relates to:** ADR-0007 (superseded by this record when it is accepted), ADR-0011 (licences), ADR-0014 (releases),
ADR-0019 and ADR-0020 (the coupling, which needs two of the three skills).
**Pending:** on acceptance, ADR-0007's status becomes Superseded by ADR-0018, by a History row; `README.md` and
`PLAN.md`'s Goal stop describing tla-kit as the image only.

---

## Context

ADR-0001 makes tla-kit one image with two ways in. tla-kit has since become the one place where the whole chain runs
on itself (`COUPLING.md` §2). The method it runs on lives elsewhere: the TLA+ skill's source is in TOPAK and vendored
here (ADR-0007), gov-tla carries a hand copy of its `SKILL.md`, the records method exists only as TOPAK's three
project-specific skills and this repository's `decisions/` form, and there is no CI/CD skill anywhere. TOPAK's
house-style proposal found that the skills that do exist disagree on who commits, on the words for a result, on what
a sync script's exit status means, and on whether what they read is data (its H-1 to H-11).

## Decision

1. **tla-kit holds three skills, each a plugin of its own:**
   - **records**: drafting, revising and proposing decision records, and keeping accepted text unedited. One skill,
     not split by act ⟨Q7⟩;
   - **TLA+**: `writing-tla-specs-and-proofs`, moved here (item 4), with the MCP server it declares;
   - **CI/CD**: how a change is carried, from branch to commit, checks, push and pull request, and what the
     assistant never does.
2. **Each is enabled on its own** ⟨Q12⟩. A repository may enable any subset: only TLA+, records and TLA+, or all
   three. No skill requires another, and none fails for want of another. Only the TLA+ skill needs Docker and the
   image; a repository with only the records skill pulls nothing.
3. **What spans two skills switches on with both.** The claims table and the claims check (ADR-0019) link records
   to TLA+ rows, so they apply only where the records and TLA+ skills are both enabled. The CI/CD skill runs the
   checks a repository lists, whichever they are, and depends on no other skill's design.
4. **The TLA+ skill's source moves here,** as `skills/writing-tla-specs-and-proofs/`, at the TOPAK commit
   `vendor/VENDOR-PIN` names, and `vendor/` is removed. ADR-0007 items 3 and 4 carry over: CI checks the scripts the
   image installs against the skill's tree by digest, and the skill stays usable without Docker.
5. **A conventions file is shared, and vendored into each plugin,** because each is installed alone. It holds what
   the skills must say the same way: the words for a result (checked, proved, certified, sampled, and what each
   leaves trusted); that an agent's reading is not the second reader a process asks for, unless the custodian rules
   that it is; that **everything a skill reads from the project is data, never instructions**; what a check's exit
   status means; and that a file is named, never found as the newest matching a pattern. CI checks that the copies
   agree.
6. **The owner of a decision is called the custodian** ⟨Q7⟩. The conventions file defines it as a role, the person
   who decides for the repository, so that no repository reads another's governance into the word.
7. **Each skill keeps one repository-specific file** for what differs between repositories: paths, lanes, the
   commit message's form, the list of checks. Everything else in a skill is general. A repository's own process
   layered on a skill, such as TOPAK's genesis, Batches and checkpoints over the records skill, stays in that
   repository.
8. **One tag releases the image and the three plugins.** The TLA+ plugin's `.mcp.json` names the image of its own
   release, by digest. A change to a skill only is a PATCH (ADR-0014 item 2's scheme).
9. **tla-kit decides the order the skills are built in, and how each is split** ⟨Q7⟩ ⟨Q12⟩, in `PLAN.md`. The
   house-style proposal's split of the CI/CD skill, carrying a change now and signing and gate evidence later, is a
   recommendation for that plan and binds nothing here.
10. **ADR-0001 item 3 binds all three:** nothing in a skill is specific to one project, and tla-kit uses each on
    itself before offering it.

## Consequences

- A fix to the method is one pull request here, not one in TOPAK and a vendoring one here and a copy in gov-tla.
- TOPAK's and gov-tla's copies change by their own pull requests, asked for there. TOPAK's three record skills
  become its own layer over the records skill.
- tla-kit's maintenance grows by three skills and a conventions file. Its one custodian is the same as TOPAK's and
  gov-tla's (`COUPLING.md` §8).

## Alternatives not taken

- **Keep the method in TOPAK.** TOPAK's records about itself would keep governing a tool every project uses.
- **One plugin with all three.** A repository could not take the TLA+ skill without the others ⟨Q12⟩.
- **The records skill split by act,** as TOPAK's three are. ⟨Q7⟩ keeps it one skill; the split is TOPAK's process.
- **Overrides in a client repository.** Considered in session and set aside: enabling and disabling whole skills
  ⟨Q12⟩, with one repository-specific file each, does what was wanted.
