# ADR-0019 — Claims are data: one table names, for each record item, the property and rows that check it

**Status:** Proposed · 2026.11.20
**Chosen by:** the assistant. `COUPLING.md` §6 lists E1 (TSV or JSON) and E2 (ids in the records' text) as the
custodian's to settle; the record takes the recommendations, and either can change before acceptance.
**State:** Drafted in part: `spec/claims.tsv` exists for both modules. No record carries claim ids yet (item 4), and
nothing reads the table (ADR-0020).
**Depends on:** ADR-0015, ADR-0016 (the modules and rows it names), ADR-0018.
**Relates to:** ADR-0020 (the check that reads it), ADR-0021 (CI).
**Pending:** none.

---

## Context

A record cites a property in a sentence: ADR-0015 item 4 lists properties by their meaning, and `spec/README.md`'s
gap table maps each fix to its record item. Nothing checks that every checked item has a property, that every
property was decided on in a record, or which rows a change to one record can reach. Each fact is already somewhere:
the verdicts in the row lists, the digests in the results files. What is missing is the link from the record item to
the rows.

## Decision

1. **Each project that takes this level keeps one claims table**, `spec/claims.tsv`: tab-separated, `#` lines for
   comments, a header row, one row per claim.
2. **The columns are these, and only these:** `claim` (a stable id, never reused), `record` (the record item that
   makes the claim), `says` (the claim in one line), `module`, `property`, `rows` (the rows that check it),
   `breaks` (the rows whose counterexample shows it is not vacuous, or `-`), and `grade` (`checked`, `proved`,
   `certified`, `sampled`, or `abstracted`, in the skill's vocabulary of claims, with `abstracted` for a property the
   module abstracts away and says so).
3. **The table restates nothing.** Verdicts stay in the row lists and digests in the results files. A claim names
   rows; whoever reads it reads those files for the rest.
4. **A record item that makes a claim carries its id** in its text, as `(C-0015-4a)`. An accepted record gains its
   ids by a History row that changes no decision text.
5. **A property that is not a claim is marked as such** in the table's comments: type invariants, conjunctions of
   claims, witnesses and the fair spec's non-emptiness. Anything else in a row list is a property nobody decided on.
6. **A heavier form may generate the table.** A project with premises and typed edges (TOPAK's specification graph)
   generates `claims.tsv` from them. The table is the floor, not the ceiling.

## Consequences

- Writing tla-kit's table found three things prose had hidden (`spec/claims.tsv`'s comments): ADR-0016 item 4 lists
  a property its module abstracts away, and the reaping property is decided in a History row with no item to cite.
  Six claims, five of PinLifecycle and one of ProveRequests, have no mutation that breaks them.
- Every record with a checked item changes once, by a History row, to carry its ids (item 4).

## Alternatives not taken

- **JSON.** Read more easily by a program, edited and reviewed less easily by a person; the row lists it sits beside
  are line-oriented.
- **Ids only in the table.** Then a checked item with no claim cannot be found: the check would only see what the
  table already names.
- **Annotations in the modules.** A module would name record items. It is the record that decides; the module checks.
