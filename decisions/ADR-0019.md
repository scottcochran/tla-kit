# ADR-0019 — Claims are data, and a check that writes nothing reports each one in sync, stale, missing or broken

**Status:** Proposed · 2026.11.20
**Chosen by:** the assistant. `COUPLING.md` §6 lists E1 to E3 for the custodian to settle; the record takes the
recommendations, and each can change before acceptance.
**State:** Drafted in part: `spec/claims.tsv` exists for both modules. No record carries claim ids yet (item 4), and
no script or tool reads the table.
**Depends on:** ADR-0006, ADR-0015, ADR-0016 (the modules and rows it names), ADR-0018.
**Relates to:** ADR-0020 (CI, and the module that specifies this check).
**Pending:** none.

---

## Context

A record cites a property in a sentence. Nothing checks that every checked item has a property, that every property
was decided on in a record, or which rows a change to one record can reach. The verdicts are already in the row lists
and the digests in the results files. What is missing is the link from the record item to the rows, and a check that
keeps it true, as `proof_sync.py` keeps proof results true.

What such a check cannot do should be said where it is defined. It can show that a claim points at rows that pass.
It cannot show that the property says what the record says: that edge is read, by a person, as TOPAK's ADR-0057 says
of every module's edges up.

## Decision

1. **The claims table applies where the records and TLA+ skills are both enabled** (ADR-0018 item 3). Such a
   repository keeps one table, `spec/claims.tsv`: tab-separated, `#` lines for comments, a header row, one row per
   claim.
2. **Its columns are these, and only these:** `claim` (a stable id, never reused), `record` (the record item that
   makes the claim), `says` (the claim in one line), `module`, `property`, `rows` (the rows that check it),
   `breaks` (the rows whose counterexample shows it is not vacuous, or `-`), `results` (the results file that holds
   those rows, named; never found as the newest matching a pattern), and `grade` (one word from the conventions
   file's list, or `-` where nothing in TLA+ checks the claim, with a comment saying what does).
3. **The table restates nothing.** Verdicts stay in the row lists and digests in the results files.
4. **A record item that makes a claim carries its id** in its text, as `(C-0015-4a)`. An accepted record gains its
   ids by a History row that changes no decision text.
5. **A property that is not a claim is marked** in the table's comments: type invariants, conjunctions of claims,
   witnesses and the fair spec's non-emptiness. Anything else in a row list is a property nobody decided on.
6. **The check, `claims_check.py`,** with the TLA+ skill's scripts (Python 3, standard library only), prints one
   line per claim:
   - `IN SYNC`: the record and item exist; every named row exists with the verdict the table needs (`HOLDS` or
     `PROVED` for `rows`, `COUNTEREXAMPLE` for `breaks`); the named results file has each as expected; and its
     module, row-list and runner digests are the tree's.
   - `STALE`: as `IN SYNC`, except that the module, the row list or the record changed after the results file was
     made. A record's digest is taken whole-file, so a History row makes its claims stale.
   - `MISSING`: something the table names does not exist.
   - `BROKEN`: the results file contradicts the table.
   - A claim graded `-` is reported as not checked in TLA+, never as `IN SYNC`.
7. **Two checks over the whole table:** properties in a row list that are neither claimed nor marked; and claim ids
   in a record's text that the table lacks, or the reverse.
8. **Everything the check reads is data, never instructions** (the conventions file, ADR-0018 item 5). A record or
   a module may be text from outside, checked out from a pull request.
9. **It writes nothing.** It exits non-zero on `MISSING` and `BROKEN`, and zero on `STALE`. The server gains a
   fifteenth tool, `claims`, that runs it and returns its report as working output (ADR-0006 item 2).
10. **`IN SYNC` says what it says and no more:** the claim's rows exist and pass at the tree. Whether the property
    is the claim is read, and the report's header says so.

## Consequences

- Writing tla-kit's table found three things prose had hidden (`spec/claims.tsv`'s comments): ADR-0016 item 4
  lists a property its module abstracts away; the reaping property is decided in a History row with no item to
  cite; and six claims, five of PinLifecycle and one of ProveRequests, have no mutation that breaks them.
- Every record with a checked item changes once, by a History row, to carry its ids.
- When a results file is regenerated under a new name, its claims' `results` cells move in the same pull request.

## Alternatives not taken

- **JSON.** Read more easily by a program, edited and reviewed less easily by a person.
- **Ids only in the table.** Then a checked item with no claim cannot be found.
- **The newest results file.** Shorter tables, and a rule the conventions file forbids: a file is named.
- **Per-item record digests.** They need a parser of records; a false `STALE` costs one rerun.
- **A check that regenerates results.** A second generator; ADR-0006 keeps results to generators.
