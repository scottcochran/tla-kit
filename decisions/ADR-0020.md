# ADR-0020 — CI requires the claims check, reruns only stale claims, and names the image; the life cycle is specified in TLA+ first

**Status:** Proposed · 2026.11.20
**Chosen by:** the custodian ⟨Q12⟩: the CI/CD skill is decoupled from these gates. The assistant chose the rest.
`COUPLING.md` §6 E4 is the custodian's to settle.
**State:** Planned. `ci.yml` reruns every row of both modules when `spec/` or `decisions/` changes, and has no claims
check. No `spec/ClaimsSync.tla` exists.
**Depends on:** ADR-0014, ADR-0015, ADR-0019.
**Relates to:** ADR-0002 (item 3), ADR-0013 (item 4), ADR-0016 (the habit item 5 follows), ADR-0018 (the CI/CD
skill).
**Pending:** on acceptance, ADR-0014 item 1 and ADR-0015 item 8 each gain a History row saying that item 2 below
replaces their "every row when `spec/` or `decisions/` changes"; no other text of theirs changes.

---

## Context

CI cannot tell which rows a change reaches, so it reruns all of them on any change to `spec/` or `decisions/`. That is
affordable at two modules and is not at TOPAK's scale. ADR-0002 item 2 says a project's results name the image's
digest; the TLC results files at `a53425b` name the jar's, in their `Checker:` line, and not the image's.

TOPAK's house-style proposal sorts what enforces a rule into four tiers: prose (a skill's text), harness (a session's
permissions), carrier (CI and the rulesets, which refuse and never admit) and mechanism. The claims check of ADR-0019
is prose until CI runs it; this record moves it to the carrier tier, and says so.

## Decision

1. **In a repository with the claims table, every pull request runs the claims check,** and its job is one of the
   required checks of `main`'s ruleset. It fails on `MISSING` and `BROKEN`. Its tier is **carrier**: it can refuse a
   merge and never accepts a record.
2. **A `STALE` claim is rerun, and only its rows.** A change to a record reruns the rows of that record's claims; a
   change to a module or row list reruns that module's claims. The check passes when every claim the pull request
   made stale is `IN SYNC` in the rerun. A checker pin move still reruns everything (ADR-0013 item 3 is unchanged).
3. **Results name the image.** The generators gain an `Image:` line, the digest `tla-kit-info` reports, when they run
   in the image. The check calls a result `STALE` if the image it names is not the one CI ran.
4. **Evidence includes the claims check of every consumer that has a table,** run in the candidate image.
5. **The life cycle is specified first,** in `spec/ClaimsSync.tla`, checked as ADR-0015 item 1 says, in TLA+ without
   PlusCal, after this record is accepted and before `claims_check.py` is written. It models an author, CI, the
   generator and the custodian, and states:
   - **No acceptance on a stale claim.** A record is never accepted while one of its claims is `STALE`, `MISSING` or
     `BROKEN`.
   - **A pass means a current result.** CI passes only if every claim's results file was made from the tree CI
     checked out, in the image it names.
   - **A rerun cannot hide a break.** A row expected to hold that now fails is reported, and no results file is
     written over it.

   Its mutations are the shortcuts: CI that skips stale claims; a generator that writes a file with a failing row;
   an acceptance that does not wait for the check; a record digest taken per item that misses a History row. Each
   breaks its property and no other. Its claims go into `spec/claims.tsv` like the others.
6. **The CI/CD skill is not part of this** ⟨Q12⟩. It runs the checks a repository lists, and the claims check is one
   of them where it exists. Neither waits on the other's design.
7. **What stays owed:** whether an acceptance is the custodian's act, and not an agent's under the custodian's
   account, is not decided by any check here. A required check is a carrier's refusal; it does not say who merged.

## Consequences

- Item 3 changes the vendored generators, made in TOPAK first under ADR-0007 and here under ADR-0018. It makes every
  existing results file `STALE` once, and each is regenerated in the current image.
- `claims_check.py` waits on the module (item 5), as `prove` waited on `ProveRequests.tla`.

## Alternatives not taken

- **Keep rerunning everything.** Correct and simple, and it hides which claims a change touched.
- **Fail on `STALE` without rerunning.** It would ask a person to regenerate what CI can.
- **The script first, the module after.** It would check what was built rather than what was meant.
