## PinLifecycle

`Mut = "none"` is the records with ADR-0015's four fixes. `M_NOF1` to `M_NOF4` each remove one fix. `M_ASWRITTEN`
is the records as they stand. It is the one mutation that removes more than one guard, because ADR-0015 item 5
asks for a row of the records as written. With every fix in force, every property holds. Each fix removed breaks
its own property and no other, and as written all four gaps show.

| Gap | Property | The counterexample, as TLC finds it |
|---|---|---|
| 1. Evidence for an image never released | `EvidenceFitsRelease` | Two pull requests, moving the jar and the base, each pass CI against the same `main`. Both merge, and the release publishes an image that neither run of evidence saw. |
| 2. A prover move with no kept copy | `BuildsFromKept` | A pull request moves the prover. CI builds the new value before any release has kept a copy of it, so it takes the value from upstream. |
| 3. Rebuilding relies on sources no record keeps | `ReleasesRebuildable` | A release is made, and then upstream stops serving the base or the jar value it holds. |
| 4. A log entry that does not name its value | `LogFiledRight` | Upstream stops serving prover 1, and the weekly check opens a served-state pull request. Then the prover move merges, and the entry is filed under prover 2. |

At these constants the model has 12,460 distinct states with every fix, and 272,854 as written.

Each fix is now written in its record: F1 in ADR-0014 item 1, F2 in ADR-0005 item 2, F3 in ADR-0013 item 8, and
F4 in ADR-0013 item 7. Writing F4 changed the model to match: an entry names its value, and a served-state pull
request whose value is no longer current is closed with nothing filed. The witness `NeverDropped` shows that this
happens.

**These results are evidence.** They were first made in an image built locally, as working output. Then they
were regenerated in the first published image, as ADR-0015 item 1 asks, and reproduced byte for byte:
`ghcr.io/scottcochran/tla-kit@sha256:454328cd…50c6`, release `v0.1.0`, whose attestation verifies
([`derived/tla-kit-phase1c-checks-2026.11.16.md`](../derived/tla-kit-phase1c-checks-2026.11.16.md)). CI compares
them on every pull request that touches `spec/`, `decisions/` or `vendor/`, or moves a checker pin
(`tools/ci/pinlifecycle.sh`, item 8).

Why `…-2026.11.15b.txt` stopped reproducing: on two liveness rows the generator then printed a state count only
when TLC's search had ended before it found the counterexample, and whether it ends first depends on the
machine. It read "12460 distinct states" on a Mac and "found before the search ended" on a GitHub runner. The
generator now prints "count not recorded" on every violated liveness row (TOPAK pull request #57).

To regenerate, from the repository root, with an image built from it:

```sh
docker run --rm -v "$PWD:/work" -e TLA_PROJECT=tla-kit tla-kit:dev \
  sh -c 'python3 $TLA_KIT_SKILL/scripts/tlc_rows.py spec/PinLifecycle-rows.txt -j 3'
```

The generator writes `PinLifecycle-results-<date>.txt` only when every row is as expected. It never overwrites a
results file: a rerun that matches says it reproduced the file byte for byte. A single row, with its trace:

```sh
docker run --rm -v "$PWD:/work" tla-kit:dev sh -c \
  'cd spec && python3 $TLA_KIT_SKILL/scripts/tlc_run.py PinLifecycle M_NOF1 EvidenceFitsRelease --expect COUNTEREXAMPLE --trace'
```

## ProveRequests

The design ADR-0016 asks for before the `prove` tool is built, in TLA+ without PlusCal, at the custodian's choice.
`Mut = "none"` is the chosen design:
- one `tlapm` per request, in a process group of its own (ADR-0009 item 5);
- a cache directory per module that the server names, held by one request at a time;
- the group killed on a timeout or a cancel;
- success read from the output, since `tlapm` exits 0 when an obligation fails;
- no response to a request the server cancelled, and none again for a cancel that arrives after the response
  (MCP 2025-06-18);
- every child reaped before the answer (the custodian's choice).

With every rule in force, all six properties hold at ADR-0016 item 5's bounds, three requests and two modules,
with one cache per module (1,486,513 distinct states) and with one shared cache (809,137). Each mutation removes
one rule, and breaks only the properties that rule guards:

| Mutation | Rule removed | Breaks |
|---|---|---|
| `M_NOLOCK` | one request at a time per cache | `OneWriterPerCache` |
| `M_KILLONE` | the group killed: only `tlapm` is, as in `marco6/tlapm-mcp` `v0.0.1` | `NoProcessOutlives`, `OneWriterPerCache` |
| `M_EXITCODE` | success read from the output: exit 0 is enough | `SuccessOnlyComplete` |
| `M_ANSWERCANCEL` | no response to a cancelled request | `AtMostOneAnswer` |
| `M_LATECANCEL` | a cancel after the response ignored | `AtMostOneAnswer` |
| `M_NOREAP` | children reaped before the answer | `AllReaped` |
| `M_DEFAULTCACHE` | `--cache-dir` given | `NothingInProject` |
| `M_NAIVE` | ADR-0016 item 5's naive design: no lock, and `tlapm` killed alone | `NoProcessOutlives`, `OneWriterPerCache` |
| `M_ESCAPE` | none: a backend may leave the process group | `NoProcessOutlives`, `OneWriterPerCache` |

`M_KILLONE` breaks two properties, not one: the backend it leaves alive keeps writing a cache the server has
released. `M_ESCAPE` is the row ADR-0016 item 5 asks for, of a backend that leaves the group. The server kills and
waits for the group only, and does not look for such a process. No backend left the group in the tests of
ADR-0016 item 6 (`derived/tla-kit-tlapm-assumptions-2026.11.16.md`), and this row shows what the choice costs if
one ever does.

Under `SpecLive`, every request is eventually answered or cancelled, and a waiting request eventually runs or is
cancelled. With one shared cache, no two runs are ever alive at once (`w-tworunning-shared`): one cache for every
module serialises every run.

**These results are evidence.** They were made natively, as working output, and then regenerated in the published
image `v0.2.0` (`sha256:5554015f…1e5d`), where they reproduced byte for byte, and again in `v0.3.0`
(`sha256:948e6d1f…257f`), the release with the tool they describe
(`derived/tla-kit-phase4-checks-2026.11.17.md`). CI regenerates them on every pull request that touches `spec/` or
`decisions/` (`tools/ci/pinlifecycle.sh … ProveRequests`).

## Working on a spec natively

For quick iteration, the skill's scripts run natively, outside the image, from the vendored copy. They need
Python 3.9 and Java 11 or newer, as the setup check says. Fetch the pinned checker once, from the repository root:

```sh
python3 vendor/writing-tla-specs-and-proofs/scripts/setup_check.py --fetch-jar
```

It downloads `tla2tools.jar` v1.7.4 into `tools/`, refuses it unless its sha256 is the pinned one, and runs the
skill's fixture rows. The jar is ignored by git and by the image's build. The scripts find it there, so `TLA_JAR`
need not be set. Then, from `spec/`:

```sh
S=../vendor/writing-tla-specs-and-proofs/scripts
python3 $S/tlc_run.py PinLifecycle M_NOF1 EvidenceFitsRelease --expect COUNTEREXAMPLE --trace   # one row, its trace
python3 $S/tlc_rows.py PinLifecycle-rows.txt --only n-none-log,n-none-kept                        # some rows
python3 $S/tlc_rows.py PinLifecycle-rows.txt -j 8 --dry-run                                        # every row
```

`--only` and `--dry-run` never write a results file. On an Apple Silicon Mac with 12 CPUs, one row takes a few
seconds and every row about a minute, against several minutes in the image under emulation.

A native run is working output: it is not made in a cited image (ADR-0002 item 7). The results file is made in
the image, as above, and CI regenerates it there on every pull request that touches `spec/` or `decisions/`
(ADR-0015 item 8).
